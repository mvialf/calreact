# PRD: Refactorización Híbrida de Arquitectura - Cobralon-FB

## 1. CONTEXTO Y PROBLEMÁTICA

### 1.1 Estado Actual
El proyecto Cobralon-FB (sistema de gestión de proyectos con Next.js + Firebase) presenta patrones de "vibecoding" que afectan:
- **Mantenibilidad**: 200+ console.logs en producción, funciones masivas (150+ líneas)
- **Escalabilidad**: Servicios con 40+ imports, componentes gigantes sin separación
- **Calidad**: TODOs pendientes, validación reactiva, deuda técnica alta

### 1.2 Evidencias Específicas
- Servicios como `projectEventService.ts` con múltiples responsabilidades
- Componentes como `ProjectForm.tsx` con symbols desconocidos
- Error boundaries complejos compensando diseño pobre
- Validación y sanitización duplicada entre servicios

## 2. OBJETIVOS DE LA REFACTORIZACIÓN

### 2.1 Objetivos Primarios
- **60% reducción** en tiempo de debugging
- **40% menos** bugs en producción
- **75% más rápido** para agregar nuevas features
- **Código testeable** y mantenible a largo plazo

### 2.2 Principios Arquitecturales
- **SOLID**: Una responsabilidad por módulo
- **DRY**: Eliminación de duplicación de código
- **KISS**: Simplicidad en diseño e implementación
- **Clean Architecture**: Separación clara de capas

## 3. ESTRATEGIA HÍBRIDA

### 3.1 Enfoque Seleccionado
**Core Clean + Migración Incremental**: Crear nueva arquitectura para servicios core, migrar componentes gradualmente manteniendo funcionalidad.

### 3.2 Razones de Selección
- Balance entre velocidad y calidad
- Permite desarrollo paralelo
- Establece patrones correctos desde el inicio
- Minimiza riesgo de regresiones

## 4. FASES DE IMPLEMENTACIÓN

### 4.1 FASE 1: Core Services Refactoring (Semana 1-2)
**Objetivo**: Crear servicios Firebase limpios con arquitectura sólida

#### 4.1.1 Patrones de Servicios Nuevos
```typescript
interface ProjectService {
  create(data: CreateProjectData): Promise<Project>
  findById(id: string): Promise<Project | null>
  update(id: string, data: UpdateProjectData): Promise<void>
}
```

#### 4.1.2 Características Técnicas
- Sin console.logs (logging estructurado)
- Funciones granulares (máximo 30 líneas)
- Validación proactiva via tipos TypeScript strict
- Error handling consistente
- Testing unitario incluido

#### 4.1.3 Servicios Prioritarios
1. `projectService.ts` - Refactoring completo
2. `projectEventService.ts` - Separación de responsabilidades
3. `clientService.ts` - Integración con nueva arquitectura
4. `paymentService.ts` - Optimización de queries

### 4.2 FASE 2: Component Architecture (Semana 2-3)
**Objetivo**: Descomponer componentes gigantes en elementos granulares

#### 4.2.1 Patrón de Componentes
```typescript
// En lugar de componente gigante
<ProjectForm>
  <ProjectBasicInfo />
  <ProjectFinancials />
  <ProjectAddress />
  <ProjectValidation />
</ProjectForm>
```

#### 4.2.2 Custom Hooks para Lógica
- `useProjectValidation()` - Lógica de validación
- `useProjectSync()` - Sincronización con Firebase  
- `useProjectEvents()` - Gestión de eventos
- `useErrorHandling()` - Manejo de errores consistente

#### 4.2.3 Componentes Prioritarios
1. `ProjectForm.tsx` - Descomposición granular
2. `NewProjectEventModal.tsx` - Simplificación de lógica
3. `AfterSaleForm.tsx` - Reutilización de patrones
4. `VisitForm.tsx` - Consistencia de UX

### 4.3 FASE 3: Clean Up & Optimization (Semana 3-4)
**Objetivo**: Eliminación de antipatrones y deuda técnica

#### 4.3.1 Limpieza de Código
- Remover todos los console.logs (implementar logger estructurado)
- Resolver TODOs pendientes en `calendarEventService.ts`
- Optimizar imports (reducir de 40+ a máximo 10)
- Implementar ESLint rules estrictas

#### 4.3.2 Testing & Validación
- Cobertura de testing al 80%+ para servicios críticos
- Integration testing para flujos principales
- E2E testing con Playwright para workflows críticos
- Performance testing para queries Firebase

## 5. HERRAMIENTAS Y TECNOLOGÍAS

### 5.1 Herramientas de Desarrollo
- **ESLint rules customizadas**: Prevenir console.logs y antipatrones
- **TypeScript strict mode**: Validación proactiva
- **Husky + lint-staged**: Quality gates en commits
- **Jest + Testing Library**: Testing comprehensivo

### 5.2 Arquitectura Técnica
- **Custom hooks**: Lógica de negocio reutilizable
- **Error boundaries granulares**: En lugar de globales masivos
- **Zod schemas**: Validación en tiempo de ejecución
- **React Query**: Gestión de estado del servidor optimizada
